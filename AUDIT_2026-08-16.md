# Audit technique Flow.io Waveshare 3.1.3 — 16 août 2026

## Verdict

La version auditée est une version fonctionnelle destinée aux essais sur banc.
Elle ne doit pas encore être considérée comme prête pour une installation de
piscine autonome sans surveillance.

Les fonctions de base ont été observées sur la carte réelle : démarrage,
interface Web par adresse IP et par `flowio.local`, Ethernet, Wi-Fi et connexion
MQTT TLS. Le code contient également des protections sérieuses autour de MQTT,
du Web et des mises à jour. Trois points restent toutefois bloquants :

1. le premier démarrage et le portail de secours exposent trop largement les
   réglages et les secrets réseau ;
2. la livraison 3.1.3 ne contient pas l’image SPIFFS correspondante ;
3. les automatismes et états sûrs ne disposent pas encore d’une validation
   matérielle exhaustive et reproductible.

Le niveau de risque global est donc **élevé pour une mise en production** et
**acceptable uniquement sur un banc contrôlé et un réseau isolé**.

## Périmètre

Cet audit concerne uniquement :

- la branche `flow.io-waveshare-3.1.3` ;
- l’environnement PlatformIO `Waveshare-ESP32-S3` ;
- la carte Waveshare ESP32-S3-ETH-8DI-8RO N16R8 autonome ;
- le firmware déclaré en version 3.1.3 ;
- SPIFFS, le Web local, Ethernet, Wi-Fi, MQTT TLS, Home Assistant, OTA, les
  entrées/sorties et les automatismes piscine exécutés par cette carte.

Les profils historiques `FlowIO`, `Supervisor`, `FlowConnectDisplay`,
`Micronova` et Wokwi n’ont pas été audités comme produits livrables.

## Méthode et limites

L’état du dépôt, le code source, `platformio.ini`, les partitions, les scripts
de livraison, le workflow GitHub Actions, le manifeste et les tests présents
ont été relus le 16 août 2026.

Les contrôles locaux suivants ont été tentés :

| Contrôle | Résultat |
|---|---|
| Version déclarée | 3.1.3 |
| Environnement par défaut | `Waveshare-ESP32-S3` |
| Taille du firmware publié | 2 133 488 octets |
| SHA-256 du firmware | `f5ff41e35f2024a962596e8ccbb91e68eb27cddbd8608b1e04e6f5b12e7304f2` |
| Budget de la partition applicative | 50,87 % de 4 194 304 octets, contrôle réussi |

| Test du script de signature OTA | non rejoué localement : OpenSSL bloqué par l’environnement d’audit |
| Campagne sur coffret réel | non réalisée dans le cadre de cet audit |

Le code contient 18 tests natifs déclarés : 10 pour la fenêtre de filtration et
8 pour les politiques Web/OTA. Le workflow CI prévoit leur exécution, mais ce
document ne prétend pas qu’un résultat CI ou matériel non observé directement a
réussi.

## Constats détaillés

### A-01 — Premier démarrage et portail de secours insuffisamment protégés

**Priorité : critique.**

Le portail de configuration Wi-Fi utilise un mot de passe commun codé en dur :
`flowio1234`. Le SSID contient un identifiant dérivé de la puce, mais le secret
du point d’accès est identique sur toutes les cartes.

Lorsqu’aucun compte administrateur Web n’est enregistré,
`allowUnauthenticatedRequest_()` autorise toutes les routes. Le jeton CSRF
protège contre une requête venant d’un autre site Web, mais il ne remplace pas
une authentification : un client présent sur le même réseau peut obtenir le
jeton puis utiliser les API.

Lorsque le portail de secours est actif, plusieurs routes de configuration
restent volontairement accessibles sans authentification. L’API
`GET /api/wifi/config` sérialise actuellement le véritable mot de passe Wi-Fi
dans sa réponse. Une personne à portée radio qui connaît le mot de passe fixe du
point d’accès peut donc récupérer les identifiants du réseau enregistré lorsque
la carte bascule en portail de secours. Sur un appareil sans compte Web, le même
risque existe depuis le réseau local normal.

Le mot de passe MQTT est mieux traité : le sérialiseur le remplace par `***` par
défaut. Le problème constaté concerne principalement les identifiants Wi-Fi et
l’absence d’authentification initiale.

**Actions obligatoires :**

1. générer un mot de passe de point d’accès propre à chaque carte avec
   `esp_random()`, ou provisionner un secret individuel de fabrication ;
2. ne jamais renvoyer le mot de passe Wi-Fi enregistré ; retourner uniquement
   un indicateur tel que `password_configured` ;
3. remplacer le mode « toutes les routes ouvertes » par un parcours de première
   installation limité et temporaire ;
4. exiger une présence physique ou un secret d’amorçage individuel pour modifier
   le Wi-Fi, MQTT et l’administrateur ;
5. ajouter des tests vérifiant les droits de chaque route dans les états
   première installation, station, portail et récupération physique ;
6. documenter l’obligation de créer le compte administrateur avant d’activer les
   automatismes.

**Critère de clôture :** une carte vierge ou momentanément privée de réseau ne
permet à aucun tiers à portée radio de lire un secret enregistré ni d’appeler
une route d’exploitation sans preuve d’autorisation.

### A-02 — Livraison 3.1.3 incomplète

**Priorité : élevée.**

Le dépôt contient `binary/flowios3-3.1.3.bin`, et son empreinte correspond au
manifeste. Il ne contient ni `binary/flowios3-spiffs-3.1.3.bin` ni entrée SPIFFS
3.1.3 dans `binary/manifest.json`. Le script `scripts/verify_release.py` échoue
explicitement sur cette absence.

Le firmware et SPIFFS doivent provenir du même commit. Utiliser l’image SPIFFS
3.1.0 avec le firmware 3.1.3 crée une livraison hybride non vérifiée.

**Actions obligatoires :**

1. reconstruire le firmware et SPIFFS depuis un commit propre et identifié ;
2. publier les deux images, le manifeste et `SHA256SUMS-3.1.3.txt` ;
3. vérifier les empreintes après téléchargement ;
4. effacer complètement une carte, flasher toutes les partitions nécessaires et
   valider l’interface Web ;
5. publier une archive d’installation initiale unique.

**Critère de clôture :** `scripts/verify_release.py` réussit et une carte vierge
peut être mise en service uniquement avec le paquet 3.1.3 publié.

### A-03 — Validation matérielle et fonctionnelle insuffisante

**Priorité : élevée.**

Le projet commande des pompes, des systèmes de dosage, un électrolyseur, du
chauffage et d’autres équipements pouvant avoir des conséquences matérielles.
Les essais déjà effectués valident l’intégration réseau générale, pas tous les
scénarios de sûreté.

La campagne manquante doit couvrir au minimum :

- les 8 entrées, leur polarité, les compteurs et les valeurs déconnectées ;
- les 8 relais sans charge puis avec les bobines des contacteurs ;
- l’état de chaque sortie au démarrage, au redémarrage et après coupure secteur ;
- les retours de contacteurs de filtration et d’électrolyseur ;
- les interlocks, temps maximaux de marche et limites journalières de dosage ;
- la perte, le court-circuit, la reconnexion et les valeurs aberrantes de chaque
  sonde ;
- les trois modes de fonctionnement, la pression, l’antigel, le chauffage, le
  robot, le remplissage et chaque régulation chimique ;
- l’apparition, l’acquittement, la persistance et la disparition des alarmes.

Les relais de la carte doivent commander des contacteurs et protections adaptés.
Le logiciel ne remplace pas les protections électriques et hydrauliques
indépendantes.

**Critère de clôture :** chaque commande et chaque défaut critique possède un
résultat attendu, mesuré sur le coffret final et consigné dans un procès-verbal.

### A-04 — Chaîne OTA de production inachevée

**Priorité : élevée.**

Les chemins OTA calculent SHA-256 et vérifient une signature ECDSA P-256. La clé
publique de production est cependant vide dans
`include/Security/OtaPublicKey.h`. Le comportement est correctement fermé : les
images signées ne peuvent pas être acceptées tant que cette clé n’est pas
provisionnée et `FLOW_ALLOW_UNSIGNED_UPDATES` vaut 0 par défaut.

Ce mécanisme évite actuellement une mise à jour non autorisée, mais ne constitue
pas encore une chaîne de livraison exploitable. Secure Boot v2, chiffrement de
la flash, protection anti-retour, rotation des clés et récupération après échec
restent à concevoir et à tester.

**Actions obligatoires :** conserver la mise à jour fermée, créer la clé privée
hors dépôt, injecter la clé publique lors de la construction officielle, signer
le manifeste et tous les artefacts, tester les corruptions et interruptions,
puis définir Secure Boot, chiffrement, eFuses, anti-retour et secours.

### A-05 — Confidentialité des secrets et du Web

**Priorité : élevée.**

La partition NVS n’est pas marquée chiffrée et aucune activation de Secure Boot
ou du chiffrement flash n’a été trouvée. Les identifiants Wi-Fi, MQTT et Web
sont donc récupérables par un attaquant disposant d’un accès physique suffisant
à la flash.

L’administration Web écoute en HTTP sur le port 80. Digest évite l’envoi direct
du mot de passe Web, mais ne chiffre ni les mesures, ni les réglages, ni les
commandes, ni les réponses contenant des secrets.

**Mesures immédiates :** ne publier aucun port HTTP sur Internet, isoler la
carte dans un VLAN d’administration, utiliser un VPN pour l’accès distant,
restreindre physiquement le port série et le connecteur de programmation.

**Mesures de production :** chiffrer la flash et NVS, terminer TLS sur une
passerelle locale de confiance ou fournir HTTPS, et prévoir sauvegarde,
restauration et rotation des secrets.

### A-06 — Compilation non parfaitement reproductible

**Priorité : élevée.**

L’environnement Waveshare référence le canal `stable` de pioarduino. Plusieurs
bibliothèques Git n’ont ni tag ni commit, et plusieurs dépendances utilisent des
contraintes `^`. Deux compilations éloignées dans le temps peuvent donc résoudre
des outils ou bibliothèques différents.

**Actions obligatoires :** figer la plateforme, le framework, les outils et
toutes les bibliothèques sur des versions ou commits précis ; conserver un
inventaire des dépendances ; documenter PlatformIO 6.1.19, Python, esptool et la
chaîne de compilation retenue ; comparer une reconstruction Windows et CI.

### A-07 — Chaîne CI à durcir

**Priorité : moyenne.**

Le workflow utilise `permissions: contents: write` pour l’ensemble du job alors
que ce droit n’est nécessaire que pour publier une release sur un tag. Les
actions GitHub sont référencées par tags (`@v4`, `@v5`, `@v2`) et non par SHA
immuable. Une compromission d’une dépendance de CI aurait donc un périmètre
d’écriture plus large que nécessaire.

**Actions recommandées :** attribuer `contents: read` au job de vérification,
isoler la publication dans un job distinct avec `contents: write`, figer les
actions sur des SHA vérifiés, protéger les tags et exiger les contrôles CI avant
publication.

### A-08 — Démarrage réseau encore couplé à la mémoire disponible

**Priorité : moyenne.**

Le serveur Web complet consomme assez de RAM interne pour avoir précédemment
empêché la vérification du certificat MQTT TLS en Wi-Fi. Le correctif 3.1.3
diffère le serveur Web jusqu’à 30 secondes si MQTT était valide au démarrage
précédent. Si la validation précédente est absente, le Web démarre immédiatement
pour permettre la correction de MQTT.

Cette politique est raisonnable, mais reste un contournement d’une compétition
de ressources. Elle n’est pas couverte par les tests natifs actuels. De plus,
les modules Ethernet et Wi-Fi pilotent tous deux l’objet mDNS global ; les
basculements répétés doivent confirmer qu’un arrêt sur une interface ne casse
pas `flowio.local` sur l’autre.

**Actions recommandées :** test d’endurance Ethernet/Wi-Fi/MQTT/Web, mesure du
plus grand bloc interne, des minima de tas, de la PSRAM et des piles ; tests des
deux chemins de démarrage ; propriétaire mDNS unique au niveau du gestionnaire
réseau ; alarme si le serveur Web ou MQTT ne devient jamais opérationnel.

### A-09 — Couverture automatique insuffisante

**Priorité : moyenne.**

Le dépôt contient 357 fichiers C/C++ d’en-tête ou d’implémentation. Les 18 tests
natifs couvrent essentiellement le calcul de filtration et quelques politiques
Web/OTA. Ils ne couvrent pas les machines d’état complètes, les routes Web
réelles, la migration NVS, MQTT, Home Assistant, les capteurs, les relais ou les
reprises après coupure.

Le fichier `WebInterfaceServer.cpp` dépasse 7 000 lignes, et les deux principaux
fichiers de logique piscine dépassent chacun 1 300 lignes. Cette concentration
augmente le coût de revue et le risque de régression.

**Actions recommandées :** tests unitaires des automatismes, tests des routes
Web et des autorisations, tests MQTT/HA, migrations NVS, tests HIL des E/S et
capteurs, puis découpage progressif des gestionnaires monolithiques.

### A-10 — Documentation secondaire à aligner

**Priorité : faible.**

Le README général, `RESTANT_A_FAIRE.md` et `docs/README.md` décrivent maintenant
l’état 3.1.3. La mise en service et le schéma de raccordement portent encore le
libellé 3.1.2, et `docs/security-hardening.md` renvoie vers
`mqtt-hardening.md`, absent du dépôt.

**Actions recommandées :** distinguer l’historique 3.1.2 des procédures
courantes, corriger les liens, mettre à jour les schémas et fournir une seule
procédure d’effacement, flash, configuration, validation et retour arrière.

## Protections déjà présentes

Les constats précédents ne doivent pas masquer les protections utiles déjà
implémentées :

- MQTT exige un nom d’utilisateur et un mot de passe ;
- `mqtt://` est refusé, TLS est imposé et le bundle de certificats ESP est
  utilisé ;
- un ancien port 1883 est migré en mémoire vers 8883 lorsque TLS est requis ;
- le mot de passe MQTT est masqué dans la sérialisation générique et les
  publications de configuration ;
- le Web fournit Digest, limitation des échecs, jeton CSRF, contrôle d’origine
  et en-têtes CSP/X-Frame-Options une fois les identifiants configurés ;
- la récupération des identifiants Web exige un appui long sur BOOT et ouvre une
  fenêtre limitée à dix minutes ;
- les mises à jour échouent de manière fermée sans clé publique et les échecs de
  signature répétés déclenchent une alarme ;
- deux partitions applicatives OTA de 4 Mio sont présentes ;
- le firmware occupe environ 50,87 % d’un slot applicatif ;
- PSRAM est activée et utilisée pour plusieurs structures volumineuses ;
- les automatismes principaux, la surveillance de pression et le robot
  automatique sont désactivés par défaut à la première installation ;
- la CI prévoit Gitleaks, Cppcheck, tests natifs, test de signature, compilation,
  contrôle de taille, génération SPIFFS et vérification des artefacts.

## Plan d’action prioritaire

### Avant tout nouvel essai connecté au réseau d’exploitation

1. corriger A-01 : mot de passe AP individuel, secrets jamais retournés et
   première installation authentifiée ;
2. créer immédiatement un compte administrateur Web sur les cartes déjà en
   service ;
3. isoler la carte sur un réseau dédié sans exposition Internet ;
4. modifier les mots de passe Wi-Fi et MQTT s’ils ont pu être exposés pendant
   les essais du portail.

### Avant la prochaine livraison 3.1.3

1. produire le couple firmware/SPIFFS et faire réussir la vérification de
   release ;
2. figer la chaîne de compilation ;
3. ajouter les tests de droits des routes Web et de démarrage MQTT/Web ;
4. exécuter un flash complet sur mémoire vierge ;
5. publier les empreintes et la procédure de retour arrière.

### Avant une installation autonome sans surveillance

1. terminer la campagne matérielle et les états sûrs ;
2. réaliser un essai d’endurance avec pannes réseau et broker répétées ;
3. finaliser OTA signée, Secure Boot, chiffrement et récupération ;
4. valider les protections électriques par un professionnel qualifié ;
5. faire déclencher chaque alarme réelle et vérifier sa notification et son
   retour à la normale dans Home Assistant.

## Conclusion

La 3.1.3 constitue une base fonctionnelle nettement avancée : l’architecture à
une seule carte est cohérente, MQTT TLS fonctionne, le Web et mDNS sont
opérationnels lors des essais réalisés, et plusieurs protections logicielles
sont déjà présentes.

La priorité immédiate n’est cependant pas d’ajouter de nouvelles fonctions. Il
faut d’abord fermer le parcours de première installation, supprimer toute
restitution de secret Wi-Fi, produire une livraison firmware/SPIFFS cohérente et
prouver les états sûrs sur le coffret réel. Tant que ces quatre résultats ne
sont pas obtenus, la version doit rester limitée aux essais supervisés.
